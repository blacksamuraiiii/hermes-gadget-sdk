## 先说清楚：为什么感觉问题这么多

先给结论，再干活——这不是设备本身一夜之间变差了，是三件事叠在同一天：

1. **10-26 一天动了五层**：字体（B1 重构 + 二级字库）、上游分流（4 项 cherry-pick + 字体语义合并）、插件（空转写双闸、relay 退出码）、USB（退避 + 限流）、唤醒接缝（分区 + Kconfig + 弱符号）。每层单独看都是小改，合在一起验证窗口就被撑大了，问题清单自然显得长。
2. **USB 掉线把所有验证都打断了**：字体验证时三次 `say` 后卡 responding、14:59 卡发不出去、验证卡要反复重发——很多“新问题”其实是同一条掉线链路的不同症状，不是五个独立 bug。掉线不解决，后面全链路测试也无法归因（分不清是唤醒没检出、还是线断了）。
3. **清单里一半不是功能 bug，是发版与文档债**：插件副本未同步、分区改动范围、阈值双标、字库数字口径、pytest 基线 18 项——这些要写进发版说明，但不影响设备能不能出声。做的时候分开记，别让债清单淹没全链路主线。

本待办的顺序就是按这个因果排的：**先定 USB（任务 0），再修唤醒接缝（任务 1），再写 port_wake（任务 2），最后合起来跑全链路（任务 3）**。顺序反了，全链路测出来的失败全是噪音。

## 出货定义：什么叫“跑通一轮”

必须同时满足，缺一环都不算跑通，且每环都要有日志/时间戳作证据，不凭“听到了”算数：

1. 说 `你好小墨` → 设备在 1 秒内亮屏并进入 Listening（日志有唤醒命中 + `audio.start`）。
2. 接着说一句话（如“现在几点”或“说一句你好”）→ 按 BOOT 一下结束录音（见任务 2 的试点约定）→ `audio.end` 发出。
3. gateway 日志出现非空 STT 转写（不是空转写、不是被 0.5s/RMS 闸拦掉），且 adapter 起了一个真实回合。
4. Hermes 回复文本上屏（中文，GB2312 全表内无 `?`）。
5. 回复经 TTS 出声播完（流式 TTS 首音延迟与播完日志都要有），设备回到 Idle、唤醒恢复待命。
6. 全程 USB 不掉线；若中途掉线，该轮作废并记入任务 0 的对照表，不算“跑通”。

试点约定（只为 10-27 跑通一轮，不等于最终产品形态）：

- 唤醒命中后**直接进 Listening**，不再停在“只亮屏”。这是对 10-26“命中只亮屏、不起回合”决定的**试点放宽**，仅用于验证全链路；正式发版是否默认起回合，等 10-27 数据出来再定。
- 录音结束方式用 **BOOT 再按一下**（tap 模式已有逻辑：Listening 下再按 Talk 即 `finish_listening()`），不新发明静默 VAD 自动结束。静默结束是 0.3 的事，明天不做。
- 试点期间测试用 gateway 的 `platforms.gadget.extra.voice` 临时改为 `true`，并确认 `speak_replies: true`。10-26 的空转写双闸已经就位（hub 侧 + adapter 侧），翻开 voice 不等于回到 0.1 的空回合 bug；试点结束是否保持开启，另行拍板。

### 0.1 已有证据（支持“hub 问题”，先写进待办，勿重查）

## 任务 1 · 修上轮意见里阻塞全链路的 bug（P1，做完才能写 port_wake）

### 1A 唤醒接缝时序（P1，第一修）

现状（`firmware/core/src/app.cpp`，`a2fc258` 引入）：`wake_resume()` 只在 `finish_listening()` 里；`cancel_listening()` 里没有 resume；`h_turn_end()` 里也没有。

后果（现在是弱符号空实现所以看不见，上 port_wake 立刻现形）：

- 正常回合：录音一结束就恢复检测，设备还在 Thinking/Responding、还在放回复音，检测器会听见自己的 TTS——设计稿的“播放静默”被接缝时序直接破掉。
- 取消路径：取消一次录音后唤醒一直停着，直到下次说话才被重新 pause，等于取消一次、唤醒死一次。

改法：

- [ ] `wake_resume()` 从 `finish_listening()` 移出，改为“回到 Idle 的所有路径统一调”：`h_turn_end()` 后回到 Idle 时、`cancel_listening()` 里、180 秒超时兜底回 Idle 时。
- [ ] `wake_pause()` 保持在 `start_listening()` 前不变；Thinking / Responding / 放音期间保持 pause，port_wake 侧不再靠“播放时自己判断 busy()”兜底（可保留作第二道，但不能是唯一一道）。
- [ ] 补 host 用例两条：取消录音后唤醒恢复；回合结束（turn_end → Idle）后唤醒恢复；录音结束但回合未结束时唤醒仍 pause。
- 验收：三条用例过；`wake_pause / wake_resume` 的调用点在代码里能一页看完，不再散落在三个函数里各写各的。

## 任务 2 · 写 port_wake，把命令词接进全链路（P0）

## 任务 3 · 全链路试点：分三段测，别一上来就合起来测

### 3A 先跑通 BOOT 按住的一轮（不带唤醒，隔离 ASR+Hermes+TTS）

目的：证明后半段本身没问题；这段不过，后面合起来测的失败无法归因。

- [ ] 测试 gateway 配置确认：`extra.voice=true`（试点）、`speak_replies: true`、STT 提供方可用、TTS 提供方可用（注意 10-23 教训：edge-tts 7.2.7 曾被微软 403 拒绝，试点前确认当前版本可用，别在全链路测试时才发现 TTS 挂了）。
- [ ] 按住 BOOT 说一句话 → 松手 → `audio.end` → STT 转写非空 → Hermes 回复上屏 → TTS 出声播完 → 回 Idle。
- [ ] 记录每跳时间戳：录音结束、STT 回来、Hermes 首字、TTS 首音、播完；空转写闸误拦时记下时长与 RMS（0.5s / RMS 80 的闸不能把正常短句拦掉）。
- 验收：连续 3 轮全过，且每轮日志链完整；任一环断了先修那一环，不进入 3B。

### 3B 再跑通唤醒检测（不带回合，隔离 MultiNet）

目的：证明前半段本身没问题；阈值扫描表是 10-27 的核心产出之一。

- [ ] 阈值扫描点 15 / 20 / 25 三档（不逐 1 微调）；每档记录：说话人（至少含用户本人）× 距离 0.5 / 1 / 2 / 3 米 × 安静 / 日常噪声两档，每档 ≥20 遍。
- [ ] 负样本库（必须跑）：日常对话 30 分钟、电视/视频 30 分钟、近音短语各 20 遍——`你好小明、你好小莫、小墨水、你好吗、墨迹、嘿、单喊一遍小墨`。
- [ ] 门槛（沿用 10-26 代办，试点可微调但要写明改了什么）：1 米安静漏唤醒 ≤5%；3 米安静漏唤醒 ≤20%；负样本合计误唤醒 ≤1 次/小时；播放期自唤醒 0 次；词尾到亮屏 ≤1 秒。
- [ ] 记录表落盘：`notes/验收-唤醒阈值扫描.md`（词 / 阈值 / 说话人 / 距离 / 噪声档 / 命中 / 延迟），不只记结论；主词超标时切备词，不用重新立项。
- 验收：选定一个阈值（默认 20，数据说了算），主词或备词至少其一达标。

### 3C 最后合起来跑通一轮（唤醒 → ASR → Hermes → TTS）

- [ ] 说 `你好小墨` → 亮屏 + 进 Listening → 说一句话 → BOOT 再按一下结束 → STT → Hermes 回复上屏 + TTS 出声 → 回 Idle、唤醒恢复待命。
- [ ] 连续跑通 **3 轮**（不是 1 轮运气好），每轮按出货定义记日志链；中途 USB 掉线则该轮作废并记入任务 0 对照表。
- [ ] 异常分支各测一次：唤醒后不说话直接按 BOOT 取消（唤醒应恢复待命，不卡 Listening）；唤醒后说一句极短/静音（应被空转写闸拦掉并回 Idle，不起空回合）；回复播报期间说唤醒词（应被播放静默拦掉，不自唤醒）。
- 验收：3 轮全过 + 3 个异常分支行为符合预期，才算“跑通一轮”的目标达成。

## 补充 · 从 rusty4444/hermes-voice-ha-integration 可学的三条（2026-10-27 用户拍板写入）

来源：`rusty4444/hermes-voice-ha-integration` v0.0.18，`plugins/voice_stack/`（主机侧 Python 插件，Porcupine/OpenWakeWord + faster-whisper/whisper.cpp，唤醒 → 录音 → STT → LLM → TTS → HA media_player）。**只学设计，不抄实现**：它是主机麦克风路径，moji 是端侧 ESP32 + USB relay，引擎代码无法直接搬到板子上；中文自定义词仍走 MultiNet 拼音路线，不换 Porcupine/OpenWakeWord（两者内置词均为英文，中文词都要另外训练）。

### 补充 1 · 唤醒接缝返回分数，不只返回 bool（接任务 1A、任务 2）

对方做法：`WakeWordEngine` 抽象 + 工厂，靠配置切换引擎；OpenWakeWord 命中按分数（>0.5）判定，Porcupine 按灵敏度（默认 0.5）判定——分数/灵敏度是接缝的一部分，不是引擎内部黑盒。

moji 落点：

- [ ] 现有 `wake.hpp` 弱符号接缝（`wake_available / wake_pause / wake_resume / wake_feed`）已对路，再往前一步：命中回调带上**分数与命令词 id**（主词/备词分别记），不要只给一个“命中了”的 bool。
- [ ] 分数进日志与阈值扫描表：同一条阈值下，命中分数分布比单纯“命中/漏检”更能指导调阈值（15/20/25 三档的取舍看分数分布定，不只看通过率）。
- [ ] 以后 mn5 换 mn6、甚至换引擎时，只换 port_wake 侧实现，core 接缝与阈值扫描表格式不动。
- 验收：阈值扫描表里每条命中都有分数与词 id；换模型时 core 文件零改动。

### 补充 2 · STT 置信度闸：低置信度先确认，不直接执行、也不静默丢弃（接任务 3A、任务 3C）

对方做法：faster-whisper 的 `transcribe_with_confidence` 用段平均 logprob 归一化出置信度，管线里低于 0.70 就不直接执行，而是问一句“Did you say: …?”。注意对方两个坑不要学：空转写时它返回的 confidence 是 1.0（靠管线先判空文本兜底）；那个“确认”循环在对方代码里还是 TODO，没真正实现。

moji 落点：

- [ ] 现状不变作基线：moji 的空转写闸用时长 0.5 秒 + RMS 80 作代理，在 Hermes 侧 STT 不返回置信度时这是合理的，不要为了套对方设计而拆掉它。
- [ ] 试点时确认一点：当前 Hermes STT 提供方是否返回置信度（或等价的段 logprob）。返回，则在 adapter 侧加一档：**低置信度 → 回设备一句确认问句（中文），不直接起回合执行**；不返回，则继续用时长/RMS 代理，并在结论里写明“无置信度可用”，不要假装有。
- [ ] 确认问句要真正走通一次（不是只写 TODO）：低置信度 → 确认 → 用户肯定/否定 → 肯定才执行、否定回 Idle；否定后不得把原转写再当命令执行。
- 验收：试点记录里有一条低置信度分支的完整日志链；无置信度时结论栏写明原因与代理方案。

### 补充 3 · 全链路分段延迟预算 + 状态计数（接任务 3C、任务 4）

对方做法：README 给了分段预算表（唤醒 250ms、STT 500ms、LLM 1800ms、TTS 300ms，合计约 2.9 秒，目标机树莓派 5），管线状态记 `last_transcript / last_confidence / total_interactions / total_errors`。注意：它的数字是目标值、不是实测结论，moji 不照抄数值，只学“分段记账”这个做法。

moji 落点（预算为 10-27 试点初值，跑完数据再修订）：

| 跳 | 试点预算 | 记什么 |
|---|---|---|
| 唤醒词尾 → 亮屏 + 进 Listening | ≤1 秒（沿用 10-26 代办） | 命中分数、词 id、阈值 |
| 录音结束（BOOT 再按）→ STT 转写回来 | ≤2 秒 | 转写文本、时长、RMS、置信度（若有） |

| TTS 首音 → 播完回 Idle | 记实测，不预设 | 播完时间、唤醒是否恢复待命 |

- [ ] 任务 3C 的 3 轮日志链按上表分段记，不要只记“跑通了”；每轮附 total_interactions / total_errors 式计数（成功轮数、失败轮数、失败环节），排障时先看计数再翻日志。

- 验收：3 轮日志链每跳都有时间戳；发布说明的延迟段落与实测表一一对应。
