# 环境：本机工具链与操作坑

- 用途：这台机器的工具链事实、本项目复现过的操作坑。通用 ESP32 经验不写这里——在技能 `esp32s3-device` 的 references。
- 核对日期：2026-10-26。验收结论见 `验收-0.1实测记录.md`。

## 工具链与构建（2026-10-26 核对）

- **ESP-IDF 在 WSL 侧**：`/home/black_samurai/esp/esp-idf`（`IDF_VER="9a97f6c5"`，工具链 `xtensa-esp-elf 15.2.0_20251204`）。`firmware/esp32/build/` 就是这个 IDF 建的，判据在 `build/project_description.json` 的 `idf_path`。
- 主机构建目录 `firmware/esp32/build/` 里 `project_version` 现为 `0.2.0`（来自 `firmware/esp32/CMakeLists.txt` 的默认 `PROJECT_VER`，可用 `-DPROJECT_VER=` 覆盖）——**它与 fork 自己的 v0.1 发布目录不是一套编号**，`hermes gadget update` 读的是前者。
- 烧录只能走 Windows 侧 COM5：WSL 看不到 `/dev/ttyACM*`；relay 独占 COM5，烧前必须停 relay（`could not open port: PermissionError(13)`）。
- 从 WSL 起全量构建会被终端工具 ~420 s 上限掐断：2000 步以上的重编用 `background=true`；被掐断后先查孤儿 `ninja.exe` 再重跑。
- **`idf.py` 必须在同一条命令里连 `export PATH=/usr/bin:$PATH` 一起做**（2026-10-26 踩到两次）：Hermes 自带 python 3.14 排在 PATH 前面，`export.sh` 会去找 `idf6.1_py3.14_env` 并失败（`ESP-IDF Python virtual environment … not found`），随后 `idf.py: command not found`。正确姿势：`cd firmware/esp32 && export PATH=/usr/bin:$PATH; unset VIRTUAL_ENV CONDA_PREFIX PYTHONPATH; . ~/esp/esp-idf/export.sh; idf.py build`，且 export 与 build 要在同一次调用里（环境不跨调用保留）。
- **烧录/抓启动日志前必须停 relay，而插件的 relay 看门狗会把它拉起来**：`relay_stop.ps1` 之后往往 1–5 秒内就有一条新 relay 进程（实测 pid 2088、580），`esptool` 随即报 `PermissionError(13)`。做法是把「停 + 烧/抓」写进同一条命令连着执行（停后 sleep 1 就开烧），失败重试 3 次；抓启动日志用一次性脚本开 COM5、按 esptool 的 DTR/RTS 序列复位再读 12–14 s（relay 抓不到启动头几行，因为它是 dtr=False 打开端口、板子早已在跑）。
- 平台检查脚本 `firmware/esp32/CMakeLists.txt:52` 会校验「生成的 sdkconfig 与 defaults 一致」：临时去掉 PSRAM 时不能只追加 `CONFIG_SPIRAM=n`，必须把板级 defaults 里的 `CONFIG_SPIRAM_MODE_OCT/SPEED_80M/USE_MALLOC/IGNORE_NOTFOUND` 一起改成 `# … is not set`，否则 cmake 直接失败（`The generated sdkconfig doesn't match its defaults`）。
- **同一 shell 里跑过别的 python 后，`idf.py` 可能报 `No module named 'pydantic_core._pydantic_core'`**：那是 `PYTHONPATH` 串了环境。固定姿势先 `unset VIRTUAL_ENV CONDA_PREFIX PYTHONPATH` 再 `. ~/esp/esp-idf/export.sh`（本机实测：带 `PYTHONPATH` 必挂）。
- `cmake`、`g++`、`node v22` 均在 WSL 侧可用；模拟器（`hermes-gadget build-sim`）未在本项目跑过。

## 操作坑（复现过两次以上）

- 打开 COM5 会复位设备（DTR），启动头 2–4 秒内发 `set`/`get` 会回 `@error ESP_ERR_INVALID_STATE`；等启动完再发即 `@ok`。
- console 命令与 relay 抢同一个串口，必须先停 relay（`taskkill /PID <pid> /F`），发完再起；`tools/console_cmd.py` 已自动让路再恢复。
- relay 必须常开：设备现在只走 USB（`server=ws://usb/gadget`），关掉就等于设备离线、提醒全哑。用 `tools/relay.sh start|stop|status` 管它——默认 `pythonw.exe` 起，**没有窗口**（`MainWindowHandle 0` 已实测），日志仍写 `tools/relay.log`；要窗口看日志就 `relay.sh start --visible`。
- **屏亮着不等于链路活着**：设备 USB 侧会假死（屏正常、无 panic、串口一个字节不来，COMx 从 PnP 消失），一晚可掉两次。先 `pnputil /scan-devices` 再拔插；relay 静默 60 s 会自己重开端口。
  - 2026-10-26 实测掉线时刻（relay.log 首个 `port missing`）：10:21:26、14:59:28 等，当日至少三次；14:51:59 重连、14:54:44 重开 COM5 后只活了约 5 分钟就再掉。掉线后 `gadget_display` 直接回 `no gadget is connected`，不是发卡逻辑的问题。
- relay 重启后设备要 30–60 s 才回来（开 COM5 会复位设备）：先出 `serial COM5 open`，才有 `hg: online (paired)`（实测 46 s）。
- **设备上电会自己装暂存固件**并再重启一轮：收尾前确认暂存镜像就是目标镜像，别把这类"意外重启"当新问题查。
- 关机流程里 `/mnt/c` 已卸载，`relay_stop` 报 `/bin/sh: 1: powershell.exe: not found`——属瞬态，重启后 gateway 会重新拉起；真按 `hermes gateway restart`（`/mnt/c` 在线）时不会出现。
- `hermes gadget update --latest` 读的是**上游** release（`plugin/releases.py` 里 `RELEASES` 写死 `Adolanium/hermes-gadget-sdk`）：fork 自己的 v0.1 不被这条路径认，本板也不在上游 manifest 里。改指向 fork 属 0.2 发版范围（`待办-20261026-v0.2.md` 1A/2.1）。

## 交接用：起 relay 与重切 cue

重启不影响 Windows 侧 relay（它是独立进程）；若 relay 是当次会话后台起的，才需重起。顺序照做：

```bash
# 1 起 relay（Windows 侧，只有它能开 COM5；pythonw 无窗口，gateway 重启不影响它）
/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe -NoProfile -Command "Start-Process -FilePath '<conda>\envs\gadget-relay\python.exe' -ArgumentList '-u','usb_relay.py','--target','ws://127.0.0.1:8765','--path','/gadget','--log-level','INFO','--log-file','relay.log' -WorkingDirectory '<repo>\tools'"
# 判据：tools/relay.log 出现 serial COM5 open 与 hg: online (paired)

# 2 三条 cue（已生成，改动文案后用这条重切）
hpy tools/make_cues.py --force
```

日常起停优先用 `tools/relay.sh start|stop|status`（插件也会按 `extra.relay_start` / `relay_stop` 自动成对起停）。
